# Easy Git

把版本管理翻译成老板能理解的工作场景。面向老板的回复只说内容会保存在哪里、谁能看到、会不会影响当前版本；不解释命令、分支或 Git 术语。

## 固定边界

- 老板只在 `develop` 工作；`master` 只由 Xiao 维护。
- 修改本地内容、保存记录、切换工作版本、合并或上传前，都确保老板已经知道“准备做什么、为什么建议这样做、会产生什么影响”。老板在明确上下文中直接说“保存”“上传”“推送”“同步”或“确认”，该命令本身就是确认，立即执行，不重复询问。
- 状态和差异检查不会改变内容，可以在确认前执行；`fetch` 及其后的操作放在确认后。
- 一次确认只授权当次已明确的动作。出现冲突、改为临时上传或需要新的取舍时，说明新的理由和影响并再次确认。
- 使用普通推送；不丢弃修改，不覆盖远端历史。
- 远端缺少 `master` 或 `develop` 时，说明仓库尚未准备好并请 Xiao 处理。

开始场景前读取适用的 `AGENTS.md`（如存在），然后只读检查当前工作位置、修改内容和远端地址。当前不在 `develop` 且存在修改时，保持原状并请 Xiao 处理。

## 怎么使用

用户问“怎么使用”“你能帮我做什么”或类似问题时，只回复下面四类能力及结果，不执行操作：

- **保存**：把当前修改安全留在这台电脑上，暂时不让其他人看到。
- **上传**：把当前修改交给 Xiao 查看；双方修改撞在一起时，先说明差异，必要时单独保存一份临时版本。
- **同步最新**：查看 Xiao 更新的正式版本；先说明变化和影响，再由老板决定是否采用。
- **查看当前状态**：说明哪些内容已保存、哪些还没上传，以及现在是否适合继续修改。

结尾说明：“每次真正操作前，我都会先告诉你为什么要做、会发生什么，等你确认后再继续。”全程只使用上面四个场景词和日常语言。

## 场景一：保存

触发示例：`保存一下`、`存一下`、`保存当前修改`。

1. 只读检查当前修改，排除临时文件、系统文件、密钥和无关内容。
2. 如果老板尚未明确要求保存，先说明准备保存哪些页面或功能；解释保存可以避免当前成果丢失，并明确“只保存在这台电脑，Xiao 暂时看不到”，然后等待确认。老板已直接要求保存时立即继续。
3. 收到确认后，按可理解的 UI 主题创建本地提交；明显不同的页面或目的分别保存。
4. 检查是否仍有未保存内容并用场景语言汇报。

没有修改时直接说“当前内容已经保存”，无需确认空操作。完成标准：确认前没有修改状态；确认后本次内容已保存且没有上传。

## 场景二：上传

触发示例：`上传一下`、`上传本地`、`发到 GitHub`、`让 Xiao 看一下`。

1. 只读检查准备上传的内容和本地保存状态。
2. 如果老板尚未明确要求上传，先说明准备让 Xiao 看到哪些变化；解释上传便于双方继续协作，并明确未保存内容会先保存，然后等待确认。老板已直接要求上传或推送时立即继续。
3. 收到确认后，保存未保存内容，确认位于 `develop`，再获取远端状态并比较本地 `develop` 与 `origin/develop`。
4. 远端没有独立新变化时，上传到 `develop`。
5. 只有远端更新时，安全更新本地后继续上传。
6. 双方都有新变化时，先汇总双方具体改动、作者、时间、影响文件及预计冲突点，并用 `git merge-tree --write-tree --quiet develop origin/develop` 在不改变工作区的情况下预判内容冲突。
7. 没有内容冲突且修改意图明确时，解释为什么可以安全合并、合并后会包含哪些变化，再次等待确认；确认后合并并上传 `develop`。
8. 存在内容冲突或无法判断应保留哪种 UI 意图时，建议把老板当前版本上传到独立临时位置。说明理由是“先让 Xiao 完整看到你的版本，同时不改变双方当前版本”，给出将使用的临时版本名称，再次等待确认。
9. 老板确认临时上传后，不创建或切换本地分支，执行 `git push origin HEAD:refs/heads/boss/upload-<YYYYMMDD-HHmm>-<shortSHA>`。名称按本地时间生成；同名时在末尾追加递增数字。

正常上传完成标准：本地 `develop` 与 `origin/develop` 一致，`master` 未变化。临时上传完成标准：老板当前提交存在于唯一的远端 `boss/upload-*`，本地和远端 `develop`、`master` 及工作区均未变化。

## 场景三：同步正式版

触发示例：`同步最新`、`同步正式版`、`把 Xiao 最新修改拿下来`。

1. 只读检查当前内容，先说明准备查看 Xiao 的正式更新；解释同步可以避免继续基于旧设计工作，并说明未保存内容会先保存。等待确认。
2. 收到确认后保存未保存内容，在 `develop` 获取远端状态，并先按“上传”场景处理 `origin/develop` 的分歧。
3. 比较 `develop` 与 `origin/master`。没有新变化时说“正式版已经是最新的”。
4. 有变化时，说明具体页面、样式或交互变化、修改人、时间、受影响内容和预计冲突点，再解释以下每个动作的用途并等待选择：
   - **先打开看看**：在隔离位置打开正式版，适合先比较外观；当前版本不变。
   - **采用这些变化**：把正式版变化加入当前版本，适合确认两边设计应该组合时使用。
   - **先不动，询问 Xiao**：保持当前版本不变，适合设计取舍还不明确时使用。
5. 老板选择后，再复述该动作的具体影响和理由并要求确认；确认后才执行。

“先打开看看”使用唯一命名的本地预览 worktree，不切换当前 `develop`，也不上传预览分支。“采用这些变化”合入 `origin/master` 并运行相关检查，但不上传，除非老板之后单独要求上传。“询问 Xiao”只生成可转发摘要。

## 冲突分析

任何分歧都先还原双方变化，不先尝试会污染工作区的合并：

```powershell
git log --date=iso --format="%h%x09%an%x09%ad%x09%s" <ours>..<theirs>
git diff --stat <ours>...<theirs>
git diff --name-status <ours>...<theirs>
git merge-tree --write-tree --quiet <ours> <theirs>
```

如果已意外进入冲突状态，记录冲突文件和双方意图，恢复到操作前的干净状态，然后重新说明理由并等待老板确认下一动作。

## 面向老板的确认与结果

确认必须包含理由和影响，不能只列选项。例如：

- `我准备保存库存页面的筛选和表格调整。这样可以防止今天的成果丢失；它只保存在这台电脑，Xiao 暂时看不到。要现在保存吗？`
- `你和 Xiao 都修改了库存页的表格结构，我无法可靠判断该保留哪一版。建议先把你的完整版本放到一个独立的临时位置，这样 Xiao 可以查看，同时双方当前版本都不会改变。要这样上传吗？`

结果先说用户获得了什么，再补必要证据。正常结果不向老板展示内部命令、提交编号或分支术语。
